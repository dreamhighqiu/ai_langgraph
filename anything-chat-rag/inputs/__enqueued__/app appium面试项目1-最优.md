### 项目一: 移动应用广告归因自动化测试平台

**项目时间**: 2024年5月 - 至今
**项目角色**: 测试开发工程师 / 核心开发
**技术栈**: Python, Appium, Pytest, ADB, MySQL, SQLAlchemy, Loguru, DingTalk API

#### 项目背景

在移动广告业务中,需要验证从用户点击广告到应用成功安装的完整归因链路是否正确。传统人工测试效率低下(30分钟/单)、易出错,且无法支持大规模测试需求。因此设计并实现了一套自动化测试平台,实现端到端业务流程的自动化验证。

#### 项目描述

负责设计并实现面向移动广告业务的端到端自动化测试平台,覆盖 Android、iOS、Amazon 三大平台,实现从广告点击到应用安装的完整归因链路自动化验证,支持多国家网络环境模拟,大幅提升测试效率和业务质量。

#### 核心功能实现

**1. 跨平台自动化测试框架 (40%)**

- **技术选型与架构设计**:

  - 使用 Appium + Pytest 构建跨平台自动化测试框架
  - 采用 Page Object 设计模式分离页面元素与测试逻辑
  - 设计 Driver 封装层统一 Android/iOS/Amazon 操作接口
  - 使用 Pytest Fixture 管理测试生命周期与设备会话
- **核心模块开发**:

  - `AndroidDriver`: 封装 Appium WebDriver,实现应用启动、元素查找、截图等功能
  - `AdbUtils`: 封装 ADB 命令,实现应用检测、WiFi 管理、Monkey 测试等
  - `FlyVpn`: 封装 VPN 连接逻辑,支持 20+ 国家自动切换
  - `OfferUtils`: 实现从数据库拉取待测数据的逻辑
- **技术难点解决**:

  - **问题**: Google Play 下载进度监控难以准确判断
  - **方案**: 通过轮询检测页面按钮状态(Install → Cancel → Uninstall)判断下载阶段
  - **问题**: 元素定位不稳定,应用商店页面经常改版
  - **方案**: 实现智能等待机制,支持多种定位策略,失败时自动截图辅助调试

**2. 广告归因链路完整性测试 (25%)**

- **业务流程实现**:

  ```
  获取 Offer 数据 → 环境检查 → 网络配置 → 生成 Click URL 
  → 打开测单工具 → 跳转商店 → 下载应用 → 安装验证 
  → 打开应用 → Monkey 测试 → 二次启动 → 清理卸载
  ```
- **关键测试点**:

  - Click URL 正确性验证(包含 token、gaid、click_id)
  - 应用商店跳转准确性(是否跳转到正确应用)
  - 下载安装流程完整性(处理各种异常提示)
  - 应用启动稳定性(连续 2 次启动测试)
  - 数据回调准确性(安装信息是否正确上报)
- **异常处理机制**:

  - 分类定义 12 种失败类型(应用已安装、网络异常、地区限制等)
  - 实现自动重试策略,失败次数超过 5 次自动跳过
  - 失败时自动截图并发送钉钉通知,包含详细错误信息

**3. 数据驱动测试架构 (20%)**

- **数据库设计**:

  - 设计 `mtg_test_tracking_auto` 表记录测试执行状态
  - 字段包含: offer_id、应用名、包名、平台、设备信息、国家、状态、执行次数、失败原因等
- **智能数据拉取逻辑**:

  ```python
  # 多维度筛选条件
  - 平台过滤: Android/iOS
  - 国家过滤: US/UK/CN 等(支持多国家)

  - 状态过滤: 排除已成功/失败超限的 Offer
  - 人工测试过滤: 排除当天已手动测试的 Offer
  ```

- **数据流转**:

  - 线上数据库(只读) → 拉取待测 Offer
  - 测试数据库(读写) → 记录执行状态
  - 测试服务器(写) → 回调安装结果

**4. 测试环境自动化管理 (15%)**

- **VPN 自动连接**:

  - 打开 FlyVPN 应用,识别并点击目标国家服务器
  - 处理 VPN 连接过程中的各种弹窗(权限、广告等)
  - 连接成功后 Ping Google 验证网络连通性

#### 技术难点与解决方案

**难点1: 应用商店下载监控**

- **问题**: Google Play 下载过程无进度 API,难以判断下载是否完成
- **解决方案**:
  - 轮询检测页面按钮状态变化(Install → Cancel → Uninstall)
  - 设置最大等待时间 30 分钟,超时则认为下载失败
  - 每 3 秒检查一次,避免过度轮询影响性能

**难点2: VPN 连接自动化**

- **问题**: VPN 应用 UI 复杂,连接过程中有多种弹窗干扰
- **解决方案**:
  - 分析 VPN 连接的完整流程,识别关键元素
  - 使用 XPath/Resource ID 定位服务器列表和连接按钮
  - 处理常见弹窗(广告、权限请求、连接确认等)
  - 连接后通过 Ping 命令验证网络切换成功

**难点3: 元素定位稳定性**

- **问题**: 应用商店页面经常改版,元素定位符失效
- **解决方案**:
  - 封装智能等待函数 `wait_for_element`,支持超时与重试
  - 失败时自动截图,快速定位是元素变化还是网络问题
  - 使用相对稳定的定位策略(Resource ID > XPath > Text)
  - 定期使用 Appium Inspector 更新元素定位符

**难点4: 多国家测试支持**

- **问题**: 不同国家 Offer 需要不同网络环境,VPN 不稳定
- **解决方案**:
  - 集成 FlyVPN 自动选择服务器
  - 实现网络连通性检测,确保 VPN 连接成功
  - 失败时记录网络状态,便于排查 VPN 问题

**难点5: 数据筛选逻辑**

- **问题**: 数据库有大量 Offer,如何选择合适的进行测试
- **解决方案**:
  - 多级过滤策略:平台→国家→时间→状态→人工测试
  - 避免重复测试:跳过已成功或失败超 5 次的 Offer
  - 随机选择机制:符合条件的 Offer 中随机选一个,避免偏向性

### Q2: 遇到过什么技术难点?如何解决的?

**回答示例:**
"在做移动端自动化测试时,遇到的最大难点是应用商店下载进度监控。

**问题背景:**
Google Play Store 下载应用时没有提供进度 API,无法直接获取下载状态,而下载时间又不固定(5秒到30分钟不等,取决于应用大小和网络速度)。

**尝试方案:**

1. 固定等待 10 分钟 → 失败,因为小应用浪费时间,大应用可能超时
2. 通过网络流量监控 → 失败,实现复杂且不准确
3. OCR 识别下载进度文字 → 失败,准确率低且耗时

**最终方案:**
我通过分析 Play Store 页面元素变化规律,发现下载过程中按钮会经历三个状态:

- Install(安装前)
- Cancel(下载中)
- Uninstall(安装完成)

因此实现了状态轮询机制:

```python
# 每 3 秒检查一次按钮状态
while True:
    if 存在 Cancel 按钮:
        说明正在下载,继续等待
    elif 存在 Uninstall 按钮:
        说明下载完成,退出循环
    else:
        异常情况,报错
  
    # 超过 30 分钟则认为超时
```

这个方案简单有效,准确率达到 100%,且能适应不同大小应用的下载。"

### Q3: 如何保证自动化用例的稳定性?

**回答示例:**
"我从以下几个方面保证自动化用例稳定性:

**1. 智能等待机制**

- 不使用固定 sleep,而是实现 `wait_for_element` 智能等待函数
- 支持超时设置,避免无限等待
- 元素出现后立即执行,提升效率

**2. 异常处理与重试**

- 对可能失败的操作(网络请求、元素查找等)添加 try-except
- 实现重试机制,失败后自动重试 3 次
- 分类记录失败原因,便于问题定位

**3. 环境隔离与清理**

- 每次测试前清理环境(清除缓存、卸载应用、重启服务)
- 测试后恢复环境,避免影响下次执行
- 使用独立测试数据,避免数据污染

**4. 失败分析辅助**

- 失败时自动截图保存现场
- 详细记录执行日志,包含每个步骤的状态
- 实现失败分类,快速识别是环境问题还是代码问题

**5. 定期维护**

- 定期检查元素定位符是否失效
- 使用 Appium Inspector 及时更新元素
- 关注应用商店页面改版,及时调整脚本

通过这些措施,我将用例稳定性从最初的 80% 提升到了 95% 以上。"
